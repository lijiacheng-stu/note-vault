你这个框架已经比较清晰了，而且**第一部分和第二部分之间的逻辑链条是成立的**：

> **动态需求统一转化 → 形成统一临机任务 → 能力可行性筛选 → 计划可行性检查 → 局部动态邻域构建 → 候选解生成 → 可行性筛选 → 最优解选择 → 局部提交**

不过目前有几个地方可以进一步理顺，尤其是**“时间窗口状态表”“局部动态邻域”“候选解”和 `temp_tag1/temp_tag2` 的关系**。我建议把整个方法组织成下面这种结构。

### 一、前置能力：卫星时间窗口状态建模

你的这个表实际上不只是“卫星时间窗口表”，因为它同时记录了**窗口当前被哪个任务占用、能够为临机任务提供什么覆盖能力，以及能够如何调整**。

可以称为：

> **卫星时间窗口动态状态表**

或者更学术一点：

> **卫星时间窗口动态状态模型**

表结构可以定义为：

|可观测范围|对应卫星|原任务|原任务窗口|能覆盖缺口的时间段|能覆盖的缺口范围|
|---|---|---|---|---|---|
|(R_1)|(S_1)|(T_1)|(W_1)|(t_1\sim t_2)|(R'_1)|
|(R_2)|(S_2)|—|—|(t_3\sim t_4)|(R'_2)|
|(R_3)|(S_3)|(T_3)|(W_3)|—|—|

其中：

- **可观测范围**：卫星在该时间窗口能够覆盖的观测范围；
    
- **对应卫星**：提供该窗口的卫星；
    
- **原任务**：当前占用该窗口的任务，可以为空；
    
- **原任务窗口**：原任务所使用的时间窗口，可以为空；
    
- **能覆盖缺口的时间段**：从该窗口中能够用于临机任务的时间段；
    
- **能覆盖的缺口范围**：该时间段实际能够弥补的临机任务观测范围。
    

这样，这张表实际上成为后续增量规划的一个**动态资源状态载体**。

# 二、第一部分：任务统一转化

这一部分的核心不是直接做规划，而是：

> **把所有动态到达的需求统一转换成“待重新规划的临机任务”。**

可以把三个算法的关系理解成：

```text
需求动态变化
      │
      ▼
任务进度保留
      │
      ▼
剩余任务评估
      │
      ▼
剩余需求
      │
      ├──────────────┐
      │              │
      ▼              ▼
原任务需求变化     外部突发任务
      │              │
      └──────┬───────┘
             ▼
        统一临机任务
             │
             ▼
       增量规划与重分配
```

### 1. 任务进度保留算法

这里建议强调一个概念：

> **不是简单保留“已经执行的任务”，而是保留“对新需求仍然有效的任务成果”。**

例如：

原任务：

[  
T_{old}: R_{old}  
]

已经完成：

[  
R_{done}  
]

需求变化后：

[  
R_{new}  
]

如果：

[  
R_{done}\cap R_{new}\neq\varnothing  
]

那么交集部分就是可以继承的有效成果。

这样就能避免因为需求变化而把已经完成的有效观测全部推倒重来。

---

### 2. 剩余任务评估算法

可以进一步形式化：

[  
R_{lack}=R_{req}-R_{all}  
]

其中：

- (R_{req})：新需求要求的观测范围；
    
- (R_{all})：已有任务成果能够满足的新需求范围；
    
- (R_{lack})：尚未满足的观测范围。
    

然后不仅计算范围缺口，还可以计算：

[  
W_{lack}=f(R_{lack})  
]

即剩余观测工作量。

这样第二部分就可以直接接收：

> **统一临机任务 + 剩余观测范围 (R_{lack}) + 剩余工作量 (W_{lack})**

而不是重新分析原任务。

# 三、突发临机任务规划

这里建议把你的算法定位为：

> **统一临机任务增量规划算法**

输入有两种来源：

### 来源1：原任务动态变化

[  
需求变化  
\rightarrow  
进度保留  
\rightarrow  
剩余任务评估  
\rightarrow  
临机任务  
]

### 来源2：外部突发任务

[  
突发任务  
\rightarrow  
临机任务  
]

最终全部进入同一个规划入口：

[  
T_{new}=  
{R_{req},t_{req},P_{req},C_{req},...}  
]

这样你论文里面“统一”的意义就非常明确了：

> **无论任务是由原任务需求演进产生，还是由外部事件突发产生，均统一转换为具有明确剩余需求和约束条件的临机任务，从而采用统一的增量规划机制进行处理。**

# 四、第二部分：计划可行性

这里你的思路其实非常好，可以明确分成**三级搜索**：

## 1. 能力可行性

第一步不要进入时间窗口冲突计算，而是先筛掉根本没有能力执行任务的卫星。

你的四个约束可以保留：

# [  
S_{candidate}

S_{space}  
\cap  
S_{time}  
\cap  
S_{accuracy}  
\cap  
S_{resource}  
]

即：

- 空间约束对齐；
    
- 时间约束对齐；
    
- 信息精度约束对齐；
    
- 资源可用性约束对齐。
    

得到：

> **候选卫星集合**

这一步实际上是在解决：

> **“谁有能力做？”**

而后面的计划可行性解决：

> **“虽然有能力，但当前计划能不能让它做？”**

这个层次划分非常合理。

# 五、2.1 空闲窗口直接插入

这里建议明确为：

> **无扰动增量插入**

即：

[  
T_{new}\rightarrow W_{idle}  
]

不改变已有任务，仅使用：

[  
W_{idle}  
]

如果能够满足：

[  
R_{lack}\subseteq R_{idle}  
]

则直接完成任务插入。

如果能够完成，就没有必要进入后面的冲突任务识别。

这相当于你的算法的**快速路径**。

# 六、2.2 局部动态邻域调整

如果空闲窗口无法满足需求，则进入你真正的核心算法。

这里最重要的是：

> **不要直接对所有任务进行全局重规划，而是围绕 (R_{lack}) 构建局部动态邻域。**

## 2.2.1 临时分配

首先把能够直接利用的空闲窗口临时分配给临机任务：

```text
空闲窗口
   ↓
temp_tag1
   ↓
计算剩余缺口 Rlack
```

`temp_tag1` 的意义可以定义为：

> **临机任务的临时占用标记**

注意它不是最终状态。

所以：

```text
temp_tag1
    ↓
后续搜索成功 → commit
    ↓
搜索失败 → rollback
```

这样语义会非常清楚。

# 七、2.2.2 冲突任务识别

你的公式：

[  
R_{lack}=R_{req}-R_{all}  
]

然后搜索能够覆盖 (R_{lack}) 的已分配窗口。

假设找到：

[  
W_1,W_2,\cdots,W_n  
]

其对应观测范围：

[  
R_1,R_2,\cdots,R_n  
]

如果：

[  
R_{lack}  
\subseteq  
\bigcup_{i=1}^{n}R_i  
]

则说明：

> 当前已有任务占用的观测窗口，从观测能力上存在覆盖需求缺口的可能。

这里我建议把“冲突任务识别”稍微改一下定义。

**此时还不能说这些任务一定冲突。**

因为现在只证明：

> **它们的窗口具备潜在替代能力。**

真正的冲突需要经过后面的：

> **时间窗口可调整性分析**

才能确定。

所以可以把这一步称为：

> **潜在冲突任务识别**

或者：

> **局部动态邻域初始集合构建**

会更加严谨。

你这个表非常重要，我建议直接把它定义为：

> **局部动态邻域候选窗口映射表**

例如：

|可观测范围|对应卫星|原任务|原任务窗口|能覆盖缺口的时间段|能覆盖的缺口范围|
|---|---|---|---|---|---|

|(R_2)|(S_2)|(T_2)|(W_2)|(t_3-t_4)|(R'_2)|

而可能是：

> 原窗口 (W_1) 中只有一部分时间能够让出/调整，并且这一部分能够覆盖 (R_{lack}) 的一部分。

因此这个表实际上把：

[

\rightarrow

\rightarrow  
可调整时间  
\rightarrow  
可覆盖缺口

串起来了。

# 九、2.2.3 候选可行解

这里你的思路本质上是在做一个**集合覆盖问题**。

初始集合：

[  
N_0={T_1,T_2,\cdots,T_n}  
]

从中选择子集：

[  
N'\subseteq N_0  
]

使：

[  
R_{lack}  
\subseteq  
\bigcup_{T_i\in N'}R_i  
]

所有满足这个条件的 (N')，构成：

> **候选解集合**

例如：

[  
{T_1,T_3}  
]

能够覆盖：

[  
R_1\cup R_3  
]

并且：

[  
R_{lack}\subseteq R_1\cup R_3  
]

那么它就是一个候选解。

# 十、2.2.4 可行解筛选

这里的 `temp_tag2` 很有意义，因为它和 `temp_tag1` 应该承担不同作用。

可以定义：

### `temp_tag1`

表示：

> **已经为临机任务临时占用的空闲窗口。**

### `temp_tag2`

表示：

> **当前候选解下，拟调整的原任务窗口。**

因此：

```text
temp_tag1
临机任务临时插入
        │
        ▼
计算 Rlack
        │
        ▼
寻找潜在冲突窗口
        │
        ▼
候选解1
   │
   ├─ temp_tag2
   ├─ 可调整性分析
   └─ rollback
        │
        ▼
候选解2
   │
   ├─ temp_tag2
   ├─ 可调整性分析
   └─ rollback
        │
        ▼
……
        │
        ▼
得到全部可行解
```

这里最关键的是：

> **每个候选解都必须在临时状态下进行完整验证，验证失败立即回滚，不污染全局计划状态。**

这就是你动态规划过程中的**事务式试探机制**。

# 十一、最优解筛选

当得到可行解集合：

[  
F={F_1,F_2,\cdots,F_m}  
]

再进行多目标评价。

例如可以考虑：

# [  
Score(F_i)

w_1C_{task}  
+w_2C_{adjust}  
+w_3C_{delay}  
+w_4C_{resource}  
+w_5C_{impact}  
]

其中：

- (C_{task})：任务完成度；
    
- (C_{adjust})：原任务调整代价；
    
- (C_{delay})：其他任务延迟代价；
    
- (C_{resource})：资源消耗；
    
- (C_{impact})：对局部计划的影响范围。
    

最终：

[  
F^*=\arg\min_{F_i\in F}Score(F_i)  
]

然后：

```text
F*
 ↓
commit
 ↓
更新卫星时间窗口动态状态表
 ↓
更新任务计划
```

而所有其他候选解：

```text
rollback
```
